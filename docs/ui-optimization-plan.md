# MeterStats UI 优化:现状盘点与待办

> 这份文件原来是一份「待确认方案」(2026-11-02),列了 P0~P3 十几项。
> 2026-11-27 逐项对着代码核实了一遍:**哪些已经做完、哪些其实不是问题、哪些还值得做**。
> 不要再按原来的条目盲目动手 —— 下面「现状」列是实测结果。

## 一、已完成 / 已不成立

| 原编号 | 原问题 | 现状(2026-11-27 实测) |
|---|---|---|
| P0-1 | 充值「待确认」徽标用了不存在的 `--warning`,靠 fallback | **已修**:改用 `var(--warn)`(`reports.js`)。全仓库 `--warning` 归零 |
| P0-2 | 351 处内联 `style="…"`,担心硬编码色值不跟随主题 | **不成立**:内联样式仍有 346 处,但**带硬编码色值的是 0 处**(全部是 `display`/`width`/`margin` 这类布局开关,或 `color:var(--x)`)。不需要大动 |
| P0-3 | Toast 与旧 alert 区块两套提示并存 | **代码层已统一**:`toast.js` 从 348 行降到 113 行(死函数在 0.5.x 清掉),`showAlert` 内部就是 `showToast`。残留的 `.alert*` CSS 规则(4 处)已在 0.5.5 删除 |
| P1-4 | 按钮体系混乱,有"第四种按钮" | **基本收敛**:现存 `btn-primary / btn-secondary / btn-danger / btn-sm / btn-xs`,死变体(`btn-ghost`/`btn-block`/`btn-danger-solid`)已删。仍有少量内联 padding 的图标按钮,可接受 |
| P1-5 | 状态色语义 badge 缺失 | **已具备**:`.badge-status` 有 `warn / success / danger / info` 四个语义变体 |
| P2-3 | 数字列没等宽数字 | **已做**:`tabular-nums` 已用在 10 处数字列 |
| P3-1 | 图标按钮缺 `aria-label` | **本轮补完**:登录页/主界面主题按钮、提醒关闭按钮都加了 `aria-label`(`index.html` 现有 4 处) |
| **P3-3** | 焦点样式弱,`:focus-visible` 0 条 | **本轮完成(0.5.6)**:按钮/链接/可聚焦容器加主题色 2px 描边(`outline-offset:2px`)。实测焦点环从「几乎看不见的浅色光晕」变成主题描边,差异 1082 像素全部落在按钮区域。**刻意不含表单控件** —— 文本控件鼠标点击也命中 `:focus-visible`,加了会每次点输入框都多一圈;而它们原本就有「边框变主色 + 3px 柔光环 + 背景提亮」 |
| P1-1(部分) | 深色主题 65 条 `[data-theme="dark"]` 逐条覆盖 | **已降到 28 条**(死规则清理的副产物)。继续 token 化的收益越来越小,风险却在上升(需逐页走查) |

## 二、仍待做(按我建议的优先级)

| 优先级 | 项 | 现状 | 建议 |
|---|---|---|---|
| — | P1-2 emoji 当图标(约 130 处在 index.html) | 未做 | **不做**。换一套 SVG 要重排导航/状态条,收益是"风格统一",但要逐页走查且影响所有主题;现方案没有明显故障 |
| — | P1-3 表格样式微差(8 个表格类) | 未做 | **不做**(除非你确实觉得某张表难看)。统一表格样式属于"看起来更整齐",但每张表的列宽/密度需求本就不同 |
| — | P2-1 弹窗 Esc 层级手写数组 | 未做(`modal_bindings.js` 里仍是手写 layers 数组) | **暂不做**。现在能正常工作;新增弹窗要手动登记是个"记得就好"的约定,写一个 Modal 管理器属于重构,收益不抵风险 |
| — | P2-2 空状态只有一行灰字(9 处「暂无…」) | 未做 | **可选**。加图标+引导按钮是纯增量改动,风险低;但属于产品口味,你说了算 |
| — | P2-4 报表/图表无加载态 | 未做 | **暂不做**。本地/局域网响应都是毫秒级(年报 31ms、月报 28ms),骨架屏只会闪一下反而更差。真要做得配合"慢查询降级"一起做 |
| — | P2-5 移动端长表单单列化 | 未做 | **待你在手机上实际用过再决定**。没有真机反馈就改布局,风险大于收益 |
| — | P3-2 表格无 `caption`/`scope`,canvas 无文字替代 | 未做(`scope=` 0、`<caption>` 0) | **可选**。`scope="col"` 是低成本高收益的屏幕阅读器改进,但要给十几张表逐个加;`caption` 需要 CSS 隐藏类配合 |
| — | P1-1(余下) 深色主题逐条覆盖 28 条 | 未做 | **不做**。剩余 28 条是组件级微调,合并进 token 需要逐个确认深色下的实际表现 |

## 三、结论

- **已经没有 P0 级问题**。原方案里最"吓人"的三条(P0-1/P0-2/P0-3)现在都不成立了:
  一条已修、一条是误判(内联样式里没有硬编码色值)、一条在代码层早已统一。
- 剩下的是**口味问题**(emoji/SVG、表格密度、空状态)和**长期重构**(主题 token 化、
  Modal 管理器、移动端布局)。它们没有对应的真实故障,不建议在没有视觉回归测试的
  前提下批量动样式 —— 这也是 0.5.4/0.5.5 两轮 CSS 清理只删"可机械验证的零引用规则"
  的原因。
- 原方案里唯一「低风险高收益」的 **P3-3 `:focus-visible`** 已在 0.5.6 做掉;剩下的都是口味问题与长期重构。

## 四、以后新增 UI 改动时怎么验证(本轮建立的做法)

项目没有视觉回归测试,所以本轮用了两条可复现的检查,建议延续:

1. **像素对比**:`chrome --headless --screenshot` 改前/改后各截一张,`PIL.ImageChops` 比 bbox。
   0.5.4 与 0.5.5 的 CSS 清理都是「除版本号文字外 0 像素差异」。
2. **结构校验**(针对 CSS 删除):解析前把注释**等长抹白**再取选择器(注释里的分号会把
   后面的活规则一起吞掉 —— 这是踩过的坑),然后断言「被删的每条选择器里所有 class 在
   全仓库零引用」且「被引用的 class 全部仍有规则」。

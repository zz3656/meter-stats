# MeterStats 模块化重构方案

> **目标**: 将当前高度耦合的单体架构拆分为独立模块，每个模块负责单一业务功能，修改某一功能时不影响其他功能。

---

## 一、当前问题分析

### 1.1 后端耦合

| 问题 | 表现 |
|------|------|
| **storage.py 是单点** | 12 个 handler 全部直接调用 `load_json`/`save_json`/`get_lock`，修改存储格式会影响所有功能 |
| **routing.py 是路由中枢** | 257 行，导入所有 handler 的所有函数，注册 ~40 条路由。新增/删除功能都要改这里 |
| **handler 交叉引用** | `admin.py` 引用 auth/users/backup_admin/admin_tools；`permissions.py` 引用 admin/settings；`backup.py` 依赖 settings |
| **_base.py 强耦合** | 所有 handler 继承 `JsonModelHandler`，共享 `_load`/`_save` 逻辑，但各 handler 数据模型不同 |

### 1.2 前端耦合

| 问题 | 表现 |
|------|------|
| **全局状态共享** | `readings` 被 7 个文件写入、15 个文件读取；`charges` 被 4 个写入、16 个读取 |
| **跨文件函数调用** | `data_fetch.js` (90 行) 调用了 35+ 个其他文件的函数，是最核心的胶水文件 |
| **同名函数冲突** | `fetchCharges`/`fetchItems` 等 6 个函数在 `core_accessibility.js` 和 `data_global.js` 同时定义 |
| **40 个 JS 文件** | index.html 直接引用 39 个 + app.js + admin.js，加载顺序决定行为 |

### 1.3 影响分析

当前修改任意一个 handler 或 JS 文件，可能影响的范围：
- **改 readings.py** → routing.py 需确认路由、storage.py 的锁/读写逻辑、前端 7+ 个 JS 文件
- **改 storage.py** → 所有 12 个 handler 可能受影响
- **改 data_fetch.js** → 35+ 个其他 JS 文件的函数调用链

## 二、模块化方案

### 2.1 模块划分

将系统拆分为 **8 个独立模块**，每个模块包含：后端 handler + 前端 JS + 测试。

```
MeterStats/
├── server.py                  # 入口 (不变)
├── routing.py                 # 路由分发 (重构为模块级注册)
├── storage.py                 # 纯存储层 (不变, 只保留 JSON 读写)
├── constants.py               # 常量 (不变)
│
├── modules/                   # [新增] 模块目录
│   ├── __init__.py            # 模块注册表
│   ├── readings/              # 抄表模块
│   │   ├── handler.py         # handle_get/post/put/delete_readings
│   │   └── __init__.py        # 导出路由和 handler
│   ├── charges/               # 充值模块
│   │   └── handler.py
│   ├── utilities/             # 水电模块 (原 readings_water)
│   │   └── handler.py
│   ├── items/                 # 物品模块 (物品+申购合并)
│   │   ├── handler.py
│   │   └── __init__.py
│   ├── duty/                  # 值班模块 (含图片上传)
│   │   └── handler.py
│   ├── reports/               # 报表模块 (月报/年报/水电)
│   │   └── handler.py
│   ├── backup/                # 备份模块 (含 admin 面板)
│   │   ├── handler.py
│   │   └── admin_handler.py
│   └── system/                # 认证/用户/设置/权限
│       ├── auth_handler.py
│       └── settings_handler.py
│
├── utils/                     # 工具层 (不变)
│   ├── api.py
│   └── audit.py
│
├── js/                        # 前端模块化 (重构)
│   ├── core/                  # 核心基础设施
│   │   ├── init.js            # 初始化 + 路由 (现有)
│   │   ├── api.js             # 统一 API 调用 (从 data_fetch 提取)
│   │   └── state.js           # 全局状态管理 (readings, charges 等)
│   │
│   ├── modules/               # 按功能拆分 (现有 js/ 重命名)
│   │   ├── readings.js        # 抄表: 录入/编辑/删除 + 展示
│   │   ├── charges.js         # 充值: 录入/编辑/删除 + 展示
│   │   ├── utilities.js       # 水电: 录入/编辑 + 展示
│   │   ├── items.js           # 物品管理: 增删改 + 借还
│   │   ├── purchases.js       # 申购流程
│   │   ├── duty.js            # 值班记录 + 图片
│   │   ├── reports.js         # 报表: 月度/年度/水电
│   │   └── backup.js          # 备份/恢复 UI
│   │
│   ├── shared/                # 共享组件 (现有部分文件)
│   │   ├── theme.js           # 主题 (core_theme.js)
│   │   ├── toast.js           # 提示 (ui_toast.js)
│   │   └── modals.js          # 弹窗 (ui_modals.js)
│   │
│   └── helpers/               # 工具函数 (现有部分文件)
│       └── utils.js           # 日期/格式等
```

### 2.2 后端架构变更

#### 当前 (现状)
```
server.py → app_handler.py → routing.py → handlers/*.py → storage.py
                                              ↓
                                          所有 handler 直接调用 load_json/save_json/get_lock
```

#### 目标 (模块化)
```
server.py → app_handler.py → routing.py → modules/*/handler.py → storage.py
                                              ↓
                                      每个模块只操作自己的数据文件
                                      (readings 模块不碰 charges 的文件)
```

**关键变更**:

1. **storage.py → ModuleStorage 抽象层**
   - 新增 `class ModuleStorage(name, data_dir)` — 每个模块持有自己的 storage 实例
   - `ModuleStorage` 封装 `load_json`/`save_json`/`get_lock`，模块无需知道存储细节
   - 现有 `load_json`/`save_json` 保留为全局兼容层

2. **routing.py → 模块自动注册**
   - 不再手动导入所有 handler 函数
   - `modules/__init__.py` 导出 `_get_routes`, `_post_prefixes` 等字典
   - routing.py 只需 `from modules import *` 然后合并路由

3. **handler 去交叉引用**
   - `admin.py` 拆分为独立的 auth/items/settings handler
   - `permissions.py` 改为配置驱动 (从 settings.json 读取权限规则)
   - `backup.py` 和 `backup_admin.py` 合并

### 2.3 前端架构变更

#### 当前 (现状)
```
index.html 直接引用 39 个 JS 文件 → 全局函数互相调用 → 同名冲突
```

#### 目标 (模块化)
```
index.html 引用 ~15 个文件:
  ├── core/init.js       (初始化)
  ├── core/api.js        (统一 API 调用)
  ├── core/state.js      (全局状态: readings, charges 等)
  ├── modules/readings.js
  ├── modules/charges.js
  ├── modules/utilities.js
  ├── modules/items.js
  ├── modules/purchases.js
  ├── modules/duty.js
  ├── modules/reports.js
  ├── modules/backup.js
  ├── shared/theme.js
  ├── shared/toast.js
  └── shared/modals.js
```

**关键变更**:

1. **State 管理器 (core/state.js)**
   - 替代全局 `readings`/`charges` 变量
   - 每个模块通过 `State.get('readings')` 读取，通过 `State.set('readings', data)` 写入
   - 提供事件机制: `State.on('readings:change', callback)` — 其他模块监听

2. **API 封装 (core/api.js)**
   - 替代各文件中分散的 `fetch('/api/...')` 调用
   - 每个模块通过 `Api.readings.list()`, `Api.charges.create()` 调用

3. **JS 文件合并**
   - 现有 37 个 js/ 文件 → 12 个模块文件 + 4 个共享文件
   - 消除同名函数: `fetchCharges` 等只保留在 `core/state.js`

4. **加载顺序**
   - core 先加载 → modules 后加载 (依赖 core) → shared 最后
   - 模块间通过 State 事件通信，不直接调用其他模块函数

## 三、实施步骤

### Phase 1: 后端模块化 (预计 3-5 天)

| 步骤 | 内容 | 风险 |
|------|------|------|
| 1.1 | 创建 `modules/` 目录结构，将现有 handler 迁移进模块 | 低 — 纯文件移动+重命名 |
| 1.2 | 创建 `ModuleStorage` 类，封装 storage.py 的读写 | 中 — 需确保并发锁正确 |
| 1.3 | 每个 handler 改为使用 `self.storage` (模块持有) | 低 — 每个 handler 独立测试 |
| 1.4 | 重构 routing.py 为模块自动注册 | 中 — 路由测试覆盖率高 (88 tests) |
| 1.5 | 消除 handler 间交叉引用 | 低 — 通过配置或 state 传递 |

### Phase 2: 前端模块化 (预计 5-7 天)

| 步骤 | 内容 | 风险 |
|------|------|------|
| 2.1 | 创建 `core/state.js` — 全局状态管理器 | 高 — 所有模块依赖此 |
| 2.2 | 创建 `core/api.js` — 统一 API 封装 | 中 — 替换所有 fetch 调用 |
| 2.3 | 合并现有 JS 文件到模块文件 (37 → 12) | 高 — 手动合并，需逐文件测试 |
| 2.4 | 更新 index.html 引用列表 | 低 — 一步到位 |
| 2.5 | 消除同名函数冲突 | 中 — 需逐文件验证 |

### Phase 3: 测试和验证 (预计 2-3 天)

| 步骤 | 内容 |
|------|------|
| 3.1 | 运行现有 88 个测试 (全部通过) |
| 3.2 | 手动测试每个业务功能 (抄表/充值/物品/申购/值班/报表/备份) |
| 3.3 | 构建 .app 并测试 macOS 端 |
| 3.4 | Docker 部署测试 |

**总计: 10-15 天**

## 五、方案对比

### 方案 A: 渐进式模块化 (推荐)
- **做法**: 新建 `modules/` 目录，逐步迁移 handler；前端逐步合并 JS
- **优点**: 风险低，随时可回滚，现有系统继续运行
- **缺点**: 过渡期两套代码共存，维护成本略高

### 方案 B: 一次性替换
- **做法**: 先完成所有模块开发，然后一次性替换 routing.py 和 index.html
- **优点**: 干净利落，无过渡代码
- **缺点**: 风险极高，一旦出错回滚困难

### 方案 C: 最小化模块 (当前方案的子集)
- **做法**: 只拆后端，前端保持现状或只做最小合并
- **优点**: 工作量减半，风险最低
- **缺点**: 前端耦合问题仍在，修改前端功能仍可能影响大范围

---

## 六、建议

**推荐方案 A (渐进式模块化)**，理由:
1. 当前系统有 88 个测试覆盖后端核心功能，可作为重构的安全网
2. 渐进迁移允许每迁移一个模块就测试一次，出问题只影响该模块
3. 前端合并工作量最大且风险最高，可以单独评估是否值得 (方案 C)

**关键决策点**:
- 前端是否需要合并? 如果只改后端不改前端，现有 JS 文件结构不变
- 是否保留 `app.js`/`admin.js`? 建议逐步淘汰，先迁移到新模块
- `storage.py` 是否保持不变? 建议保持全局兼容层，新增 ModuleStorage 抽象
